# Log Observatory MCP – jury setup and award demonstration

This is a local **stdio MCP server**, in addition to the Streamlit application.
An MCP host discovers seven fixed read tools and chooses which to call. The same
SereneDB functions power both interfaces; SQL calculates, the host's model explains.
The server itself makes **no model/API calls** and needs **no OpenAI key**.

## 1. Prepare once (Windows / PowerShell)

Use the [repository quick-start](../README.md) to create `.venv`, start Docker,
load the complete BGL/OpenStack corpus and configure `DB_DSN` in the ignored
repository `.env`. The official technical guidance supplies no shared database,
loader, schema or ownership table; this repository implements them locally.
`ingest/configure_local.py` creates the app's SELECT-only database login. Reuse
that login for MCP; tool annotations alone do not enforce database privileges.
Installing or checking MCP does not modify the database or create a login.

From the repository directory:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-mcp.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m mcp_server.check
.\.venv\Scripts\python.exe -m mcp_server.config
```

The check starts the real server in a separate process **outside the repository
working directory**, negotiates MCP, discovers the tools/prompts, calls all seven
tools against the local database and reads back their evidence resources. It
requires the full corpus and writes `out/mcp-protocol-check.json`. No LLM or API
key is involved. Expected final status: `passed`, seven tools, zero LLM calls.
The default checks the older initialize handshake (`2025-11-25` with SDK 2.3.0),
and `--mode auto` also tests the current protocol negotiation.

Other team members/judges must generate their **own absolute paths** using
`python -m mcp_server.config` in their environment. No passwords or API keys
belong in this JSON. The server reads `.env` relative to the repository, even if
Claude launches it from a different directory. An already-set `DB_DSN` environment
variable takes precedence over `.env`.

Completely quit/restart Claude Desktop and check that `log-observatory` exposes
**seven tools**. Start a new conversation, enable this server, and try the demo
questions below. The host launches the server automatically. Manually running
`python -m mcp_server` just waits for JSON-RPC on stdin; it does not start a web
page. No Node.js runtime is needed for this Python server.

Desktop/Code, rather than a public connector URL for a browser-hosted chat.

## 3. Tools, prompts and evidence contract

| Tool | When the host should choose it | Query/result limit |
|---|---|---|
| `corpus_overview` | Discover actual team names, dataset counts and historical date bounds first | 100 dataset/team rows |
| `search_logs` | Engineer locates symptoms, IDs and matching-line counts | Default 20, max 50 log rows |
| `get_context` | Engineer follows a log, exact VM UUID or request ID | Default 50, max 100 rows; BGL window max 3,600 s |
| `vm_dauer` | Compare a VM's spawn duration with the OpenStack baseline, including INFO anomalies | Default top 5, max 20, plus a selected observation when needed |
| `top_patterns` | Team Lead compares recurring templates and reach | Default 10, max 30 templates |
| `pattern_trend` | Lead/Manager checks one template/team over historical time | At least template/team required; max 10,000 query buckets |
| `priority_ranking` | Manager weighs frequency, severity, reach, trend and BGL alerts | Default 20, max 100 groups |

The discoverable JSON schemas constrain inputs (no extra arguments, bounded
limits, dataset/level enums, ISO dates and known intervals). Annotations mark
all tools as read-only, non-destructive and local. The server exposes no free
SQL, shell commands, ingestion, database administration or arbitrary file reads.
Missing functions and database failures are explicit errors, never simulated
results or a misleading zero-match response. Requests run one at a time in each
server process. Limits bound returned data, **not query execution time**; a client
timeout does not guarantee cancellation of a synchronous database query.

Each successful call returns the same object in text and `structuredContent`:

```text
evidence_id, evidence_uri, tool, arguments,
result: { sql, zeilen, daten, meta, ... },
view: { truncated, changes, ... }
```

`result.sql` is executed SQL, not a model-generated proposal. Supporting queries
and metadata remain in the underlying response. The model preview (`result` +
`view`) is at most **32 KiB**. Primary and nested tables share a 70-row preview
budget, with at most 50 rows per table; long text/arrays may also be shortened.
Every shortening is marked by its JSON path in `view.changes`. `zeilen` and SQL
aggregates retain their original meanings; `shown_items` is just the preview
length. Tool-level `truncated`/`meta.gekuerzt` remain separate from MCP preview
truncation. Never calculate full-corpus distributions from these samples.

Read the returned `evidence://<sha256>` URI through MCP `resources/read` for the
**unmodified full tool response**, including executed SQL. This is still limited
by the database tool; it is not an unlimited export of all raw logs. Responses
above **1 MiB** are rejected with a request to narrow the scope. The in-memory
evidence cache holds at most **24 responses / 8 MiB**, uses LRU eviction, and
disappears on server restart. Evidence is local to that server process; an
expired/unknown URI explicitly fails and must be regenerated by calling the tool.

`resources/list` exposes the guide (`logs://guide`) and currently cached evidence.
`resources/templates/list` describes evidence URIs. Three reusable MCP prompts
(`engineer_investigation`, `team_lead_review`, `manager_priorities`) accept a
required `question` and optional `dataset`/`team`. Host support for displaying
resources/prompts varies; tool calls work independently of those UI features.

Server instructions tell the host to treat log messages as untrusted data,
separate observations/hypotheses/checks and cite log/template IDs plus evidence
URIs. This helps guide model behavior; it is not a guarantee against incorrect
answers. BGL timestamps preserve the ingestion's local-time-labelled-UTC
convention. OpenStack traceback rows are not separate incidents, and spawn
observations must not silently be renamed distinct VMs.

## 4. Three short award-demo questions

Use a fresh conversation per role and keep the MCP tool calls visible. The model
should select tools itself; the paths below are expectations, not scripted tool
outputs. Start with: **Use Log Observatory MCP and SQL evidence. State scope,
uncertainty and truncation; separate observations, hypotheses and next checks.**

1. **Engineer / OpenStack:** “Why is VM
   `544fd51c-4edc-4780-baae-ba1d80a0acfc` unusual? Compare its spawn duration with
   the baseline and inspect its context.” Expected: `vm_dauer` + `get_context`;
   actual SQL supports 41.81 s vs median 19.7 s, rank 2 among 2,066 spawn
   observations. INFO-only context does not rule out a performance anomaly.
2. **Team Lead / HPC Kernel / BGL:** “What problems recur in our team? Compare
   their frequency and affected nodes, then inspect a historical trend.” Expected:
   `top_patterns` + `pattern_trend`; explain why event/line counts differ in
   multiline data and which dataset/time period the figures describe.
3. **Manager / BGL:** “Should we investigate data TLB error interrupt or data
   storage interrupt first? Explain frequency versus reach and the score.”
   Expected: `search_logs` + `priority_ranking` and optionally `pattern_trend`;
   compare BGL-0019 and BGL-0119 rather than inventing cost or claiming proven
   causation. The most frequent pattern need not have the greatest reach.

For the special award, save a short **actual Claude recording/transcript** showing
the connection, discovered tools, the chosen calls and an evidence-based answer.
Include the setup instructions and a screenshot of visible SQL/evidence. A Python
protocol test proves interoperability mechanics, **not** that Claude has already
selected the tools correctly or answered well. The team's Claude end-to-end test
remains a separate acceptance step until its recording/transcript is saved.

## 5. Verification and troubleshooting

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_mcp_server -v
.\.venv\Scripts\python.exe -m mcp_server.check --mode auto --output out/mcp-modern-check.json
```

The unit tests use explicitly artificial fixtures, not disguised database data.
They cover both handshake modes, strict validation before DB access, errors and
secret redaction, original-evidence retrieval, result/cache limits, all three
prompts and launching from a different working directory. The separate SQL check
uses the real complete corpus. See the [recorded protocol check](evidence/mcp-protocol-check.json).

Recorded on 18 October 2026: **100/100 project tests passed** with real database
tests enabled. A fresh Python **3.12.14** environment installed only
`requirements-mcp.txt` (no OpenAI SDK), passed dependency checking and all nine
MCP tests, and completed all seven real-data calls plus the traceback regression.
The existing app environment also passed both MCP protocol modes
(`2025-11-25` and `2026-07-28`). No model calls were made for this MCP validation.
These results include Eren's context/citation fixes from `202edc2`.

If discovery works but calls fail, check Docker/tables and `.env` privately.
Use `127.0.0.1`, not `localhost`, in `DB_DSN`. After reloading tables restore the
read-only grants using the root README steps. On a partial corpus the check
intentionally fails its expected row-count assertions. If discovery fails,
regenerate the absolute launcher paths, install `requirements-mcp.txt` in that
same Python environment and restart the host. Keep all debug output on stderr:
stdout belongs exclusively to MCP JSON-RPC. Claude Desktop's MCP logs are under
`%APPDATA%\Claude\logs`.

Implementation uses the [official MCP Python SDK](https://py.sdk.modelcontextprotocol.io/)
2.3.0, including its [legacy-client support](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/).
